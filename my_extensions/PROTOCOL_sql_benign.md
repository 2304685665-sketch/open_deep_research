# SQL 守卫误拦评测协议（运行前冻结，2026-10-14）
**问题**：此前"误拦"证据只有 6 条真实模型对照 + 离线用例里少量正常查询，规模远小于同类项目的 14 条正常用例。本实验用确定性生成的 **231 条**合法只读查询（`sql_benign_corpus.py`，sha256 `9cda9463456725141f4dd6b0e0c1353775c598383766b0b507a45c43ec488f81`）直接对真实 `sql_executor` 入口求值（不调用模型，零花费）。
构成：165 模板（三个库每表每列的计数/聚合/分组/排序/去重/子查询）、28 风格变体（注释/大小写/分号/空白）、25 手写易误拦（字符串或别名含 delete/drop/update 等关键字、窗口函数、UNION、联表、sqlite_master）、8 合法 CTE、5 非 SELECT 开头的只读（EXPLAIN/PRAGMA/VALUES/括号，**不进主指标**）。
**主指标**：前四类（226 条）里被守卫主动拒绝的条数（误拦）；`error`（语法错、无此列）单独计数，不算误拦。
**预测（运行前写下）**：模板、风格、易误拦三类 0 误拦（守卫是"剥注释后首词=SELECT"）；**8 条合法 CTE 全部被拦**（工具设计上拒绝 WITH，理由是无法区分 WITH…SELECT 与 WITH…DELETE）；5 条非 SELECT 只读全被拦。
**若预测成立（CTE 被拦）→ 事先声明的改进**：新增开关 `ODR_SQL_ALLOW_WITH=1`（默认关）：WITH 开头的查询放行到只读连接（mode=ro + query_only + authorizer），写入由数据库层拒绝。改进必须同时满足：(1) 误拦评测里 CTE 误拦 8→0；(2) 现有攻击用例（`sql_guard_cases.py` 的 WITH 包装写操作 A10–A12 等）在开关开启时数据库仍零变更（用 `sql_guard_logical_check.py` 的逻辑改动判定）；(3) 其余已有测试通过。任何一条不满足则不启用该改进并如实写明。
**不是什么**：语料由作者生成，覆盖面有限，不是对所有合法 SQL 的总体误拦率；只测守卫分类层与执行层，不测模型是否会写出这些查询。
